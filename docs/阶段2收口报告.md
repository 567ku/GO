# 阶段2收口报告 - WebSocket底座一致性改进

## 一、收口任务概述

阶段2 WebSocket 模块开发已基本完成，本次收口针对三个一致性改进点：

### 收口1：时间工具一致性
**问题**：工厂函数使用 `time.Now().UnixMilli()`，而项目已有统一函数 `model.NowMs()`  
**目标**：统一使用 `model.NowMs()` 增强代码一致性

### 收口2：精度注入准备
**问题**：Market/UDS 解析时假设精度（临时硬编码），存在运行时偏差风险  
**目标**：标记 TODO，准备从 `QtyConfig` 注入 `pricePrecision/qtyPrecision/quotePrecision`

### 收口3：Trade回包转换说明
**问题**：TradeClient 将响应回灌到 `pending.RespChan`，后续转换逻辑不清晰  
**目标**：添加详细注释，说明在 Executor/Manager 侧统一转换为 `ExecutorResultEvent`

#### pkg/ws/trade.go - handleMessage
**修改前**：
```go
// 发送到响应通道（不阻塞）

```

**修改后**：
```go
// 阶段2收口：当前TradeClient将响应回灌到pending.RespChan（请求相关性）
// TODO(phase3): 在Executor/Manager侧统一转换为ExecutorResultEvent并发给Engine
// 转换逻辑参考：pkg/model/types.go:349-361 (ExecutorResultEvent定义)
// 确保双保险闭环的数据源一致：TradeWS回包 + UDS订单更新
// 发送到响应通道（不阻塞）
select {
case pending.RespChan <- wsResp:
default:
}
```

**关键设计说明**：
1. **当前实现**：TradeClient 只负责请求相关性（通过 `pending map` 匹配请求和响应）
2. **后续阶段**：在 Executor 或 Manager 侧统一转换为 [`ExecutorResultEvent`](c:\Users\Administrator\Desktop\GO2.0\pkg\model\types.go#L349-L361)
3. **双保险闭环**：
   - 数据源1：TradeWS 回包（快速反馈）
   - 数据源2：UDS 订单更新（权威数据）
   - 两者必须保持一致性，避免状态分歧

4. 与 UDS 的 `OrderUpdateEvent` 形成双保险闭环

**验收标准**：
- Engine 能同时接收 TradeWS 回包和 UDS 订单更新
- 状态机能正确处理两种数据源（快速反馈 vs 权威数据）
- 无状态分歧或死锁
